# DSH 拆分用量统计与多 Agent 工作方式复盘

整理日期：2026-09-12。统计日期：2026-09-11，北京时间。

## 1. 结论

本次拆分存在两个相互放大的问题：

1. **丢失最终目标。** “先复制功能，再实现修改”在后续合同中逐步收缩成迁移及主区视觉替代。原生 Session 列表、固定后端、一对一 main thread 绑定，以及 main 主区/subagent 副区没有持续约束实现与验收。局部修复和检查不能自动证明最终目标完成。
2. **任务派发颗粒度与上下文生命周期不匹配。** 按小步骤分批派发，却反复交给同一个长期运行的 agent。既承担了小任务的分派、等待、交接和复审成本，又保留了长任务的上下文积累。

用户最终明确的工作原则是：**同一个目标，一开始交完整任务列表；不同目标，使用独立上下文。`def_coding_worker` 应接小而明确的独立任务。** 不是禁止复用 agent，也不是要求所有任务都拆小。

## 2. 统计范围与口径

- 时间窗口：北京时间 2026-09-11 00:00–24:00，即 UTC 09-10 16:00–09-11 16:00。跨日执行只计窗口内请求，不是整个拆分项目生命周期总额。
- 来源：本地 `~/.codex/state_5.sqlite` 会话索引；按 DSH 项目 cwd 与后代关系定位，再提取相关 rollout 的用量、模型、推理等级、工具名称及额度字段。
- 按线程核对 `thread_id`，在线程内按 `response_id` 去重，累加 `token_usage_record.payload.usage` 单次值；不把累计 `thread_token_usage` 重复求和。
- 未大范围阅读执行报告或展开工具结果正文；仅有限抽查协调调用结构。消息正文为不透明编码，未解码，不能据此逐项计算返工比例。
- 这是本地逐请求记录统计，不是订阅账单。输入包括重复上下文与缓存输入；不能把 token 总数直接换算为实际费用或订阅周额度。
- 当次统计脚本位于本机临时路径 `/tmp/dsh-usage-audit.py`，可能被系统清理；本文件保留统计方法、结果和关键线程身份，不依赖该临时文件才能阅读。

## 4. 消耗集中点

### 4.1 主协调反复处理长上下文

线程 `01a08df7-b663-77e2-9dad-554596972c3e`，Sol medium：

- 153,221,930 token；1,134 次模型请求。
- 平均每次输入 134,917 token，最大 239,331 token。
- `wait_agent` 520 次，`followup_task` 171 次，`send_message` 89 次，`list_agents` 31 次，`spawn_agent` 14 次。
- 按模型响应所发工具分类，829 次响应仅含协调类调用，占约 73.1%，对应约 112,430,738 token，占任务总量约 19.4%。这不是对所有协调内容的精确语义成本划分，也不表示这些 token 全可消除。

等待时间本身不消耗 token；每次回到模型判断是否继续等、询问状态或追加任务，会重新处理上下文。缓存命中降低部分成本，但不意味着无限次协调免费。

### 4.2 小批次持续进入同一个实现上下文

实现线程 `01a08f69-a10e-7e30-adcd-95d80bb637fd`，路径 `/root/b1b_c2_b2a`，Sol medium：

- 145,450,069 token；1,078 次模型请求。
- 25 个 turn，8 次上下文压缩，平均输入 134,497 token。
- 主协调向其发送 24 次 followup。

任务名被持续复用，不能把该线程后续全部用量归给最初 B1b/B2a。数字说明它实际承担的是长期连续工作，而非一次短小委托。

### 4.3 规划、审查与验证的往返

- Planner `/root/review_requirements_v2`：Astra high，246 次请求、40 个 turn；主协调向其发送 39 次 followup。
- Reviewer `/root/b1a_simplicity_review`：Sol high，383 次请求、24 个 turn；主协调向其发送 23 次 followup。
- 验证线程 `/root/phase5_no_model`：58,186,000 token、465 次请求、40 个 turn。`no_model` 指被测阶段不启动产品模型对话，不代表验证 agent 自身不使用模型。

反复往返次数可以量化，但在未逐条读取正文的情况下，不能精确声称其中多少轮是必要修复、重复检查或无效返工。

## 5. 周额度的实际观察

旧周窗口在当天首条相关记录显示已用 38%，北京时间 23:08:29 首次显示 100%。23:27:14 出现不同 reset 标识的新窗口，显示 0%；23:52:59 显示 2%。

能确认当天耗尽了当时剩余的周额度。不能据此断言当天单独用了完整 100% 周额度，也不能判断新窗口来自换账号、重置或其它原因。记录是账户额度快照，不能把每个百分点精确归因到某个 agent。

## 6. 两个根因如何放大成本

**目标丢失主要降低投入的产出价值。** 实现者满足当前合同，Reviewer 找局部缺陷，Planner 调整合同，Dispatcher 推进批次；如果合同已遗漏原始目标，这些环节可以全部正常运转，却仍交付错误的产品形态。此前权限、恢复、审批等修复有实际价值，但不能代替原生用户会话目标。

**细拆与长上下文混用主要放大执行成本。** 同一目标的已知步骤分批追加，使 agent 无法从开始就按完整依赖和验收安排工作；每批又带来协调、解释和审查。若是不同目标，却继续复用该上下文，则会携带无关历史。

两者结合，形成“在越来越长的上下文中，通过越来越多的交接完善偏离目标的结果”。本次统计支持协调规模很大；已确认的产品偏差支持目标漂移结论。没有逐次反事实实验，不能给出精确的浪费 token 比例。

## 7. 以后如何分派

| 情况 | 任务交付方式 | 上下文生命周期 |
| --- | --- | --- |
| 同一目标，步骤强相关、需要共享理解 | 一开始交完整目标、任务列表、依赖顺序、边界和最终验收；由负责人自行推进内部步骤 | 同一 agent 连续完成，保留相关上下文 |
| 不同目标，彼此独立 | 分别提供各自需要的输入和验收，不继承无关工作史 | 使用独立上下文 |
| `def_coding_worker` | 小而明确、可独立完成和验收的任务；输入足够，不要求它重建全项目决策 | 完成即结束；下一件不同目标的小任务使用新上下文 |
| 跨模块、强耦合的产品目标 | 交给能够承担完整目标的 agent，不先切碎再靠 followup 拼回 | 同一负责人持有从需求到结果的连续理解 |
| 独立验证/复审 | 在候选与验收范围明确后交付有界检查，返回具体发现和证据 | 隔离于实现上下文；有新修复才检查受影响部分 |

followup 用于新事实、真正的需求变化、纠偏或阻塞恢复；不把一开始已知的下一步骤反复当成新任务派发。阶段划分可以保留，但阶段可以是同一完整任务内的检查点，不必成为新的 agent 往返。

最终用户行为必须持续可见。技术接点失败要报告具体能力缺口，不能静默删除需求；“先迁移后修改”不能在交接时变成只验收迁移结果。当前产品目标与修正计划见 [下一步入口](./NEXT-STEPS.md)。

## 8. Astra 直接做是否更好

判断：让 Astra 连续负责本次核心主线——需求理解、原生接入、关键实现和真实界面核对——大概率比本次重协调方式更合适。原因是 Session 身份、首次发送、列表、主副区和恢复强耦合；减少交接有利于保留目标，并减少重新解释与分派。

但昨天 Planner 已是 Astra high。问题不是简单的“没有用强模型”，而是模型被放在反复修改合同的位置，未连续负责产品结果。把相同的细拆、等待和目标漂移原样换成 Astra，并不能消除成本；更高单价还可能增加费用。

建议是 Astra 或其他能承担完整目标的负责人做核心主线，少量独立任务才委托子 agent；完成关键实现后进行有界独立审查。不是规定所有阶段单 agent，也不是认为便宜 worker 不适合编码。`def_coding_worker` 适合输入明确的小任务；不能让它通过大量往返承担未经明确授权的整项目理解。

上述是针对本次任务的反事实判断，没有同任务单 agent / 多 agent 对照实验，不能承诺具体节省比例、一次成功或成本必然下降。

官方资料作为机制背景，而非本项目效果证明：

- [Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents)：独立并行任务可受益，多 agent 通常增加 token，写入密集的并行工作增加协调风险。
- [GPT-6 Astra](https://developers.openai.com/api/docs/models/gpt-6-astra)：模型定位与价格说明；API 单价不等同于本次订阅额度计算方式。
